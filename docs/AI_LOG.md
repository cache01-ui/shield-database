# Журнал взаємодії з ШІ (вайбкодинг)

**ШІ-інструмент:** Claude Code (модель Claude Opus 5.5, Anthropic) — агент у застосунку Claude Desktop,
що має доступ до файлів проєкту, терміналу та вбудованого браузера.
**Роль розробника:** формулювання вимог, вибір рішень, перевірка й приймання результату.
**Період:** листопад 2026.

## 1. Вимоги та критерії приймання

Вимоги сформульовано на основі ЛР № 1–4 та завдання ЛР № 5:

| № | Вимога | Критерій приймання |
|---|---|---|
| В1 | Клієнтська частина з ЛР № 3–4 працює без змін для користувача | усі 10 сторінок відкриваються, немає помилок у консолі |
| В2 | Дані досьє, загроз та інцидентів зберігаються в БД і віддаються через REST API | `GET /api/...` повертає JSON, сторінки будуються з відповідей API |
| В3 | Повний CRUD для польових рапортів | створення, перегляд, редагування, видалення через інтерфейс і API |
| В4 | Перевірка даних на клієнті **й** на сервері | некоректний запит → `400` з помилками полів |
| В5 | Базова безпека | параметризовані SQL-запити, екранування виводу, CSP, ліміт запитів, секрети в `.env` |
| В6 | Доступність і продуктивність | ARIA-атрибути, клавіатура, стиснення та кешування статики |
| В7 | Автотести API | `npm test` — усі тести проходять |
| В8 | Розгортання | конфігурація Render, застосунок доступний за публічною адресою |

## 2. Початковий промпт (специфікація)

Рішення, обрані розробником у діалозі з ШІ (див. крок 2 нижче), зведено в специфікацію:

```
Перетвори статичний сайт S.H.I.E.L.D. (ЛР 1–4) на вебзастосунок.
Архітектура: клієнт (наявні HTML/CSS/JS у public/) ↔ REST API (Node.js + Express) ↔ SQLite.
Дані: перенеси масиви досьє, загроз, інцидентів із JS-файлів у таблиці БД (початкове наповнення з JSON).
Нова сутність «Польовий рапорт»: id, title (5–120), agent (формат LVL7-COULSON), location (≤120),
priority (low|medium|high|critical), status (draft|active|closed), incident_id (FK → incidents, необов'язково),
body (20–4000), created_at, updated_at. Повний CRUD: GET список (пошук q, фільтри status/priority), GET :id,
POST → 201, PUT :id → 200, DELETE :id → 204; помилки — JSON {error, fields} зі статусами 400/404.
Клієнт: Fetch API + async/await, стани «завантаження/помилка/порожньо», нова сторінка «Рапорти»
з формою в <dialog>, підтвердженням видалення, перевіркою полів.
Безпека: Helmet + CSP (лише власні скрипти), express-rate-limit на зміну даних, параметризовані запити,
серверна валідація, обмеження розміру JSON, налаштування через змінні середовища.
Вхід залишити як у ЛР 4 (перевірка формату без облікових записів).
Додай тести node:test, README, .gitignore, render.yaml для Render.
```

## 3. Хід роботи

### Крок 1. Аналіз завдання
**Промпт розробника:** «[файл Лабораторна_робота_5.docx] і останне)»
**Відповідь ШІ:** прочитав завдання, перевірив середовище (Git є, Node.js відсутній), запропонував рішення
та поставив 4 уточнювальні запитання перед суттєвими змінами.

### Крок 2. Вибір рішень (відповіді розробника)
| Питання ШІ | Рішення розробника |
|---|---|
| Встановити Node.js LTS через winget? | Так |
| Яку сутність робити з повним CRUD? | Польові рапорти (нова вкладка) |
| Робити справжні облікові записи з хешуванням паролів? | Ні, залишити вхід як у ЛР 4 |
| Де розгортати? | Render |

### Крок 3. Середовище
- Встановлено Node.js 26.13.1 (`winget install OpenJS.NodeJS.LTS`), перевірено вбудований `node:sqlite` (SQLite 3.54).
- **Рішення ШІ:** використати `node:sqlite` замість `better-sqlite3`, щоб уникнути компіляції нативних модулів на Windows.

### Крок 4. Структура та дані
- Клієнт перенесено в `public/`, дані з `threats.js`, `incidents.js`, `dossiers.js` — у `server/data/*.json`.
- Створено схему БД (`server/db.js`) з обмеженнями `CHECK`, зовнішнім ключем і індексами.

### Крок 5. Сервер і REST API
- `server/app.js`, `server/routes.js`, `server/validation.js`, `server/index.js`.
- Встановлено залежності: `express@5`, `helmet`, `express-rate-limit`, `compression`; `npm audit` — 0 вразливостей.

### Крок 6. Клієнт
- `public/api.js` — єдина функція `apiRequest()` із таймаутом і класом `ApiError`.
- Матриця загроз, журнал інцидентів, профілі переведено на запити до API; пошук загроз — із затримкою (debounce)
  та скасуванням застарілих запитів через `AbortController`.
- Нова сторінка `reports.html` + `reports.js` (CRUD), вкладка «РАПОРТИ» на всіх сторінках, сторінка 404.
- Inline-скрипт профілю досьє винесено в `dossier_profile.js` — **цього вимагала політика CSP**.

### Крок 7. Перевірка
- `npm test`: 8 тестів API (стан, пошук, фільтр, 404/400, повний CRUD, помилки валідації, некоректний JSON,
  заголовки безпеки) — **усі пройшли з першого запуску**.
- Перевірка в браузері: усі сторінки отримують дані з API, CRUD через форму, фільтри, лічильники.
- Перевірка XSS: рапорт із `<img onerror>` і `<script>` у полях відображається як текст.

### Крок 8. Репозиторій і розгортання
- Створено Git-репозиторій, коміт із адресою `cache01-ui@users.noreply.github.com` (захист email розробника).
- Під час перегляду `git status` виявлено, що правило `data/` у `.gitignore` виключало `server/data/` з початковими даними — виправлено на `/data/`.
- Код опубліковано: https://github.com/cache01-ui/shield-database.
- Розгортання на Render (Blueprint з `render.yaml`): https://shield-database-tzrr.onrender.com.
- Перевірка на сервері: `/api/health` → 200; сторінки → 200; неіснуюча адреса → 404; CRUD: POST 201, PUT 200, некоректний POST 400, DELETE 204, GET видаленого 404.

## 4. Помилки, знайдені під час перевірки ШІ-коду

| Що виявлено | Як виявлено | Виправлення |
|---|---|---|
| Обробник клавіші «/» падав з `TypeError: event.target.closest is not a function` (ЛР 4) | консоль браузера | перевірка `event.target instanceof Element` |
| Матриця загроз запитувала неіснуючі `*.png` → помилки 404 | журнал сервера | виправлено шляхи до зображень |
| Inline-обробник `onerror` суперечив вимогам ЛР 4 | рев'ю коду | обробник `error` на фазі занурення |
| Inline-скрипт у `dossier_profile.html` блокувався б CSP | аналіз політики безпеки | винесено в окремий файл |
| Перевірка сторінок через `<iframe>` не працювала | консоль: `frame-ancestors 'none'` | це очікувана дія захисту від clickjacking; перевірку виконано прямою навігацією |
| Правило `data/` у `.gitignore` виключало `server/data/` | перегляд `git status` перед комітом | правило змінено на `/data/` |
| Генератор звіту ЛР 3 двічі екранував XML (у документі видно теги) | рендер DOCX у PDF | виправлено обробку вже готових фрагментів |

## 5. Висновки щодо використання ШІ

- ШІ пришвидшив створення шаблонного коду (маршрути, схема БД, форми, тести), але кожне рішення
  перевірялося тестами, у браузері й валідаторами.
- Суттєві рішення (встановлення ПЗ, вибір сутності, автентифікація, хостинг) ухвалював розробник.
- Ризики ШІ-коду (вразливості, «неіснуючі» API, помилки в граничних випадках) мінімізовано
  автотестами, серверною валідацією, `npm audit` та ручною перевіркою.
